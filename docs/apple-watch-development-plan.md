# План разработки приложения для Apple Watch

## Обзор

Этот документ описывает детальный план разработки приложения для Apple Watch с сокращенным функционалом по сравнению с основным iOS-приложением. Приложение для часов будет поддерживать выбор типа активности на день и выполнение тренировок с синхронизацией данных между часами и iPhone.

## Цели и ограничения

### Функционал для часов

- Выбор типа активности на сегодняшний день из 4 вариантов (`DayActivityType`):
  - `workout` - тренировка
  - `stretch` - растяжка
  - `rest` - отдых
  - `sick` - болезнь
- Выполнение тренировки (если выбран тип `workout`):
  - Упрощенный интерфейс выполнения тренировки
  - Сохранение результата тренировки
- Синхронизация данных между часами и iPhone:
  - Двусторонняя синхронизация через WatchConnectivity
  - Синхронизация выбранных активностей
  - Синхронизация результатов тренировок
  - Синхронизация номера текущего дня программы

### Ограничения

- Минимальный UI для часов (ограниченный размер экрана)
- Упрощенная логика тренировок (без сложных настроек)
- **Часы не хранят данные локально** (исключение — запись завершённых тренировок в HealthKit, store на самих часах) - все данные запрашиваются с iPhone и сохраняются через iPhone в SwiftData
- **Статус авторизации и номер текущего дня** передаются через WatchConnectivity (см. «Обмен данными между часами и iPhone»)
- **Текущий день** получается только из WatchConnectivity (готовый номер дня); при отсутствии связи действия с iPhone не выполняются (ошибка логируется) — `AuthRequiredView` показывается только при отсутствии авторизации
- **iPhone приложение является единственным хранилищем данных** (SwiftData)
- **Приложение для часов работает только после успешной авторизации в iPhone приложении** (авторизация гейтит UI; запись завершённых тренировок в HealthKit от связи с iPhone не зависит — см. «Интеграция с HealthKit»)

### Обмен данными между часами и iPhone

#### WatchConnectivity Service

**Архитектура связи:**

- iPhone - единственное хранилище данных (SwiftData)
- Часы не хранят данные локально (исключение — запись завершённых тренировок в HealthKit) - все данные получаются только через WatchConnectivity в реальном времени
- Все действия с часов передаются в iPhone через WatchConnectivity (`sendMessage`)
- Статус авторизации и номер текущего дня передаются через WatchConnectivity

**Команды синхронизации:** (см. «Команды WatchConnectivity» в разделе «Технические детали»)

**Механизмы передачи данных:**

- `sendMessage` - для немедленной передачи данных, требует активного соединения
- `updateApplicationContext` - для передачи данных, работает даже когда приложение на часах закрыто (без поля "command")

**Формат данных:**

- JSON для передачи сложных структур
- Простые типы (Int, String, Bool) для простых команд

#### Обработка push-канала состояния на часах

- Пуш статуса (`PHONE_COMMAND_AUTH_STATUS`) и `applicationContext` обязаны обрабатывать и наличие, и **отсутствие** значений: отсутствие ключа `currentActivity` при известном `currentDay` означает удаление активности — локальное значение сбрасывается в `nil` (ветки в `handleApplicationContext` и кейсе `.authStatus` `WatchConnectivityService`).
- Причина: уведомление UI идёт через `didSet` `currentActivity` с guard'ом `!= oldValue`. Если сервис остаётся с протухшим значением, повторный пуш того же значения глушится guard'ом, и home-экран рассинхронизируется (см. «Решённые проблемы» в разделе «Интеграция с HealthKit»; регрессионный тест `HomeViewModelAuthStatusActivityTests`).

#### Разрешение конфликтов при одновременном изменении активности

**Проблема:**
При одновременном изменении активности на один и тот же день с разных устройств (часы и iPhone) могут возникать конфликты. Например:

- На iPhone начали тренировку (создана активность `.workout`), но не закончили и свернули приложение
- На часах выбрали активность "отдых" для того же дня
- Без специальной обработки активность будет перезаписана на "отдых", что приведет к потере данных о тренировке

**Стратегия разрешения конфликтов:**

1. **Приоритет незавершенных тренировок:**
   - Если на день уже существует активность типа `.workout` (тренировка), изменение на другой тип активности (`.rest`, `.stretch`, `.sick`) отклоняется — на часы возвращается ошибка
   - Это предотвращает случайную потерю данных о начатой тренировке
   - Проверка выполняется на iPhone при обработке команды `WATCH_COMMAND_SET_ACTIVITY` от часов

2. **Last Write Wins (LWW) для других случаев:**
   - Для активностей типа `.rest`, `.stretch`, `.sick` применяется стратегия LWW на основе `modifyDate`
   - Последнее изменение побеждает (обновляется `modifyDate` при каждом изменении)

3. **Проверка перед изменением:**
   - При получении команды `WATCH_COMMAND_SET_ACTIVITY` на iPhone:
     - Проверить существующую активность для указанного дня
     - Если активность существует и имеет тип `.workout`:
        - Отклонить изменение (вернуть ошибку на часы); запрос подтверждения не реализован
      - Если активность не существует или имеет другой тип - выполнить изменение

4. **Уведомление пользователя (не реализовано):**
   - Ошибка возвращается на часы в replyHandler, но часы в текущей реализации reply не читают (`sendActivityType` резолвит continuation без проверки) — сообщение об ошибке на часах не показывается

5. **Специальный случай - завершенные тренировки:**
   - Если тренировка завершена (есть `count` и `duration`), изменение на другой тип активности разрешено
   - Это позволяет пользователю изменить активность после завершения тренировки

**Реализация:**

- Логика проверки конфликтов реализуется в `StatusManager` на iPhone при обработке команды `WATCH_COMMAND_SET_ACTIVITY`
- Используется `DailyActivitiesService` для проверки существующей активности
- При обнаружении конфликта возвращается ошибка на часы через WatchConnectivity (replyHandler)
- Часы в текущей реализации reply с ошибкой не обрабатывают — сообщение пользователю не показывается

**Примечание:**

- Эта стратегия применяется только для конфликтов между часами и iPhone

## Ключевые архитектурные решения (часы)

### Архитектура хранения данных

- Часы не хранят данные локально — все данные получаются только через WatchConnectivity в реальном времени; исключение — запись завершённых тренировок в HealthKit (store на самих часах, на iPhone синхронизируется системой)
- iPhone — единственное хранилище данных (SwiftData), часы работают как клиент
- Синхронизация через WatchConnectivity: `sendMessage` (оперативно) + `updateApplicationContext` (доступен и при закрытом приложении); при отсутствии связи действия не выполняются (см. «Ограничения»)

### Формат передачи данных

- Используются **модели с Codable** для прямой передачи данных (без DTO)
- Команды передаются как **строковые enum** (WatchCommand: "WATCH_COMMAND_SAVE_WORKOUT")
- Данные сериализуются через JSONEncoder/JSONDecoder
- Пример: `{"command": "WATCH_COMMAND_SAVE_WORKOUT", "result": {...}}`

### Команды WatchConnectivity (резюме)

- Расширенный набор команд с явными названиями, более детальное разделение команд (отдельно для активности и тренировки)
- Команды проверки авторизации не нужны — статус передается через WatchConnectivity (`sendMessage`)

### Авторизация

- Обязательная проверка авторизации при запуске, блокировка функционала, экран `AuthRequiredView`
- Статус авторизации передается через WatchConnectivity

### Обработка данных тренировки

- Данные тренировки передаются через модели с Codable (`WorkoutData`, `WorkoutResult`)
- Сохранение по одной активности/тренировке, немедленная передача на iPhone без локального сохранения (кроме записи завершённой тренировки в HealthKit)

### Синхронизация

- Часы → iPhone: сохранение результата тренировки и изменение/удаление активности; iPhone → часы: актуальные данные (real-time запрос + push)
- Часы запрашивают данные с iPhone в реальном времени, нет очереди синхронизации
- При отсутствии связи действия не выполняются (ошибка логируется)

### Стек

- Swift + SwiftUI для часов
- SwiftData на iPhone (не используется на часах)

### Преимущества текущего подхода

1. **Упрощенная архитектура:**
   - Нет дублирования данных между часами и iPhone
   - Конфликт активностей разрешается приоритетом незавершённой тренировки на iPhone (см. «Разрешение конфликтов при одновременном изменении активности»)
   - Проще поддержка и отладка

2. **Актуальность данных:**
   - Данные всегда актуальны (запрашиваются в реальном времени)
   - Рассинхронизация после сохранения устранена (см. «Обработка push-канала состояния на часах»)

3. **Безопасность:**
   - Обязательная проверка авторизации
   - Данные хранятся только на iPhone, кроме записи завершённых тренировок в HealthKit на самих часах

4. **Современные технологии:**
   - SwiftUI вместо WatchKit
   - SwiftData вместо CoreData
   - Codable модели вместо ручной сериализации JSON и DTO

### Недостатки текущего подхода

1. **Зависимость от связи:**
   - Часы не могут работать полностью офлайн
   - Требуется постоянная связь с iPhone для работы

2. **Производительность:**
   - Каждый запрос требует связи с iPhone
   - Может быть медленнее при плохой связи

3. **Ограничения:**
   - Меньше автономности часов
   - Зависимость от доступности iPhone

## Интеграция с HealthKit

### Текущее состояние (v1 — реализовано)

- **Что записывается:** завершённые на часах тренировки типа «тренировка» — `crossTraining`, длительность, даты начала/конца. Растяжка, отдых и болезнь не пишутся (нет флоу выполнения с длительностью); прерванные (`isInterrupted`) и записи без дат не пишутся.
- **Запись только с часов:** HealthKit-стор на самих часах, на iPhone синхронизируется системой. Тренировки с iPhone не пишутся — отдельный будущий план (capability iOS, ключи Info.plist, guard `HKHealthStore.isHealthDataAvailable()`).
- **Запись не зависит от WatchConnectivity:** тренировка попадает в «Здоровье», даже если передача на iPhone не удалась.
- Live-подтверждено на паре Ultra 4 ⇄ iPhone 17 (watchOS 27 / iOS 27): диалог показан, `HKWorkoutBuilder.finishWorkout()` записывает `HKWorkout`. Финальная валидация на реальных Apple Watch — при появлении устройства.

### Архитектура реализации

- Протокол `HealthKitWorkoutWriting` (DI через init-параметр), реализация `HealthKitWorkoutWriter`: запрос разрешения (`HKWorkoutType`, `read: []`) и сохранение через `HKWorkoutBuilder` (`beginCollection` → `endCollection` → `finishWorkout`, без живой сессии). Deprecated-инициализатор `HKWorkout(start:end:)` не используется.
- Ошибки — OSLog на русском, best-effort: недоступность или отказ HealthKit не мешает сохранению в SwiftData и основной работе.
- **Точка запроса разрешения:** вход в превью тренировки — `.task` (`requestHealthKitAuthorizationIfNeeded`): идемпотентно, не блокирует загрузку данных, отменяется при уходе с экрана.
- **Точка записи:** после успешной отправки на iPhone (`saveTrainingAsPassed`); повторное сохранение не дублирует запись (гейт `lastWorkoutResult`).
- Обратная совместимость: `WorkoutResult` декодирует старый JSON без полей дат (`init(from:)` с `decodeIfPresent` и дефолтами).
- Тесты: `WorkoutPreviewViewModelHealthKitTests` (пропуск прерванных, дедуп), `setsCanStartTrainingToFalseWhenLoadFails`, `HomeViewModelAuthStatusActivityTests` (обе — см. «Решённые проблемы»).

### Разрешения и конфигурация

- Entitlement `com.apple.developer.healthkit` + `NSHealthUpdateUsageDescription` (en: «The app saves completed workouts to the Health app.»; ru: «Приложение сохраняет выполненные тренировки в приложение «Здоровье»»). Тумблер отключения не делается — отзыв разрешения системный.
- Отложено до расширения: `NSHealthShareUsageDescription` (чтение пульса/калорий), `WKBackgroundModes = [workout-processing]`.
- **Переигровка системного диалога** (отладка на watch-симуляторе): (1) Настройки часов → Конфиденциальность и безопасность → Здоровье → выключить тумблер записи; (2) `simctl uninstall` — ненадёжен для HK-permissions; (3) `simctl erase` — надёжно, крайний случай. `simctl privacy` не имеет сервиса `health` — особенность тулчейна.

### Ограничения и правила

- **Дубликаты:** в v1 источник один (часы), повторное сохранение не дублирует запись. Правило для будущего iPhone-плана: каждая тренировка пишется ровно один раз — с устройства, где выполнена; iPhone не переписывает watch-тренировки, пришедшие по WatchConnectivity.
- **Одна workout-сессия одновременно:** при расширении до `HKWorkoutSession` чужая параллельная сессия даёт `errorAnotherWorkoutSessionStarted` — логировать через OSLog, не ломать сценарий завершения тренировки.

### Будущее расширение: пульс и калории

Цепочка для живой сессии: `HKWorkoutConfiguration` (`.crossTraining`, `.indoor`) → `HKWorkoutSession` → `associatedWorkoutBuilder()` (`HKLiveWorkoutBuilder`) → `HKLiveWorkoutDataSource`.

- Источник данных сам собирает релевантный набор метрик для типа активности (пульс, активные калории) — ручной `enableCollection(for:)` не нужен (в референсе явный сбор только пульса приводил к пустому обработчику калорий).
- Статистика — через делегат `workoutBuilder(_:didCollectDataOf:)` → `statistics(for:)`: пульс (count/min), калории (kcal) → проброс в UI.
- Завершение: `session.end()` → `endCollection(withEnd:)` → `finishWorkout` — билдер сам создаёт и сохраняет `HKWorkout`.
- Чтение при расширении: `.heartRate`, `.distanceWalkingRunning`, `.activeEnergyBurned`, `.workoutType` + ключ `NSHealthShareUsageDescription`.

**Приоритеты:** высокий — отслеживание пульса и калорий во время тренировки; низкий — интеграция с другими метриками HealthKit (шаги, активность); общие улучшения — см. «Приоритеты разработки».

### Решённые проблемы

- **Бесконечный блюр при открытии превью** (HK-диалог блокировал `loadData`, при `sessionUnavailable` открывался пустой `fullScreenCover` без dismiss): запрос вынесен в `.task` превью, computed `canStartTraining` блокирует кнопку «Начать тренировку» при ошибке загрузки; регрессионный тест `setsCanStartTrainingToFalseWhenLoadFails`. Follow-up: понизить до `.debug` оба лога `loadData`, `HK authorization requested` и маркер тапа «Начать тренировку» после 2+ недель стабилизации.
- **Рассинхронизация активности после сохранения** (пуш `AUTH_STATUS` с тем же значением глотался guard'ом didSet): deletion-ветка в `.authStatus` — см. «Обработка push-канала состояния на часах»; регрессионный тест `HomeViewModelAuthStatusActivityTests`.

### Замечание для отладки логов

`Logger.info`/`warning` не попадают в `simctl log show` на watchOS-симуляторе (видны только `.error` и системные) — использовать консоль Xcode / `log stream`. Не путать с «код не логирует».
