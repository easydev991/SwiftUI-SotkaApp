# План: интеграция SotkaApp с приложением «Здоровье» (HealthKit)

## Цель

Тренировки, завершённые на **Apple Watch**, должны отображаться в «Здоровье» на iPhone (и в Активность, Фитнес). **Записываем в HealthKit только тренировки с часов:** у Watch есть доступ к пульсу и метрикам (при `HKWorkoutSession`), данные синхронизируются на iPhone. Тренировки только с iPhone в HealthKit не пишем — запись с iPhone вынесена в отдельный будущий план (там понадобятся capability iOS, ключи Info.plist и guard `HKHealthStore.isHealthDataAvailable()`: на iPad HealthKit нет). Записываем только активность типа «тренировка»; растяжка, отдых и болезнь не записываются (нет флоу выполнения с длительностью).

## Текущее состояние

HealthKit не используется (см. [apple-watch-development-plan.md](../apple-watch-development-plan.md)). Завершение тренировки на часах: `WorkoutViewModel.finishWorkout()` → `WorkoutResult` → превью (`WorkoutPreviewViewModel.handleWorkoutResult`; в iOS-таргете одноимённый класс — `SwiftUI-SotkaApp/Screens/WorkoutPreview/WorkoutPreviewViewModel.swift`) → по тапу «Сохранить» `saveTrainingAsPassed()` → `WatchConnectivityService.sendWorkoutResult` (WC-команда `saveWorkout`) → на iPhone `StatusManager.handleSaveWorkoutCommand` → `WorkoutProgramCreator` → SwiftData. Модели: `DayActivity`, `WorkoutResult(count, duration)`, `SaveWorkoutData`.

> Примечание: ранее на часах завершение тренировки обрабатывал `WatchWorkoutService` — удалён в ходе overengineering-аудита; его роль выполняют `WorkoutViewModel` и `WatchConnectivityService`.

## Технические детали (референс реализации)

Конфигурация, проверенная по работающей ObjC-реализации того же продукта, плюс требования из документации Apple. Источник решений для этапов ниже.

### Сессия на часах (для расширения с пульсом/калориями)

- `HKWorkoutConfiguration`: `activityType = .crossTraining`, `locationType = .indoor`.
- Цепочка: `HKWorkoutSession` → `associatedWorkoutBuilder()` (`HKLiveWorkoutBuilder`) → `HKLiveWorkoutDataSource`.
- В референсе сбор явно включался только для пульса (`enableCollection(for: .heartRate)`), из-за чего обработчик калорий оставался пустым. По документации, если `typesToCollect` не менять вручную, источник сам собирает релевантный набор для типа активности (включая пульс и активные калории) — для нас дефолт предпочтительнее.
- Старт: `startActivity(with:)` + `beginCollection(withStart:)` в момент начала тренировки; длительность — wall-time от старта сессии (подтверждает правило дат из Этапа 1).
- Делегат `workoutBuilder(_:didCollectDataOf:)` → `statistics(for:)`: пульс текущий/средний/мин/макс (`count/min`), калории — сумма (`kcal`) → проброс в UI.
- Завершение: `session.end()` → `endCollection(withEnd:)` → `finishWorkout { }` — билдер сам создаёт `HKWorkout` и сохраняет его в HealthKit store, дополнительная запись не нужна.
- Запись в HealthKit **не зависит от WatchConnectivity**: тренировка попадает в «Здоровье», даже если передача на iPhone не удалась (синхронизация store↔store — см. «Требования Apple»).

### Разрешения

- Запрос: share = `[.workoutType]`; read (только при расширении до чтения пульса/калорий): `.heartRate`, `.distanceWalkingRunning`, `.activeEnergyBurned`, `.workoutType`.
- В референсе запрос выполнялся на часах при каждой активации главного экрана после проверки `HKHealthStore.isHealthDataAvailable()`. Достаточно одного запроса перед первым обращением к HealthKit — в этом плане моментом выбран первый вход в превью (метод — Этап 4, точка вызова — Этап 5), что требованию удовлетворяет.
- Ключ Info.plist обязателен под запрашиваемую операцию, иначе приложение **падает** при запросе авторизации (доки HealthKit): `NSHealthUpdateUsageDescription` — запись, `NSHealthShareUsageDescription` — чтение. В v1 чтения нет — `NSHealthShareUsageDescription` отложено (см. Этап 3). С watchOS 6 форма разрешений показывается на самих часах.
- Рабочие русские формулировки из референса: «Разрешить обновление Здоровья» (запись) / «Разрешить делиться данными Здоровья» (чтение).

### iPhone

- В референсе iPhone запрашивал share = workout, но ни разу не записывал тренировки; фоновая доставка пульса (`enableBackgroundDelivery`, frequency = immediate) и `HKObserverQuery` имели пустой обработчик — мёртвый код. Вывод: в v1 iOS-таргет HealthKit не затрагивает вообще (см. Этап 3).

### Требования Apple (документация)

- Для watchOS предпочтительный путь — `HKWorkoutSession` + `HKLiveWorkoutBuilder`; `finishWorkout(completion:)` создаёт и сохраняет `HKWorkout` автоматически.
- Простая запись без сессии — `HKWorkout(activityType:start:end:)` + `HKHealthStore.save` — валидный API; `duration` считается из дат.
- На Apple Watch одновременно может идти только одна workout-сессия — ошибка при чужой сессии и её обработка (актуально при расширении) описаны в «Рисках».
- HealthKit-сторы iPhone и часов синхронизируются системой автоматически; старые данные на часах периодически выгружаются (`earliestPermittedSampleDate`). На v1 не влияет: мы создаём `HKWorkout` напрямую, без чтения и подписок.
- `WKBackgroundModes = [workout-processing]` в Info.plist Watch-приложения — сессия продолжается в фоне.

Для первой версии — простая запись `HKWorkout` по датам (см. Этап 4); полная схема (сессия + пульс/калории) — при расширении.

## Этап 1: Доменный слой и контракт сервиса HealthKit

- [ ] Определить **что записывать в HealthKit** для одной тренировки:
  - v1 (простая запись `HKWorkout`): тип активности `HKWorkoutActivityType.crossTraining` (как в плане по часам, см. «Технические детали») и даты (правило ниже). Тип локации в v1 не записывается: `HKWorkoutSessionLocationType` — параметр `HKWorkoutConfiguration` живой сессии, в инициализатор `HKWorkout` не передаётся; если indoor-метка понадобится — через метаданные `HKMetadataKeyIndoorWorkout`;
  - v2 (живая сессия, при расширении): тип локации `HKWorkoutSessionLocationType.indoor` берётся из `HKWorkoutConfiguration` (см. «Технические детали»);
  - `startDate` и `endDate` — правило: `startDate` = `workoutStartTime` из `WorkoutViewModel`; `endDate` = момент `finishWorkout()` (`Date()`). `WorkoutResult.duration` для вычисления дат не использовать: в коде `duration = workoutTime + totalRestTime` (`WorkoutViewModel.swift:290–296`), а wall-время уже включает периоды отдыха — иначе отдых учтён дважды;
  - доставка в точку вызова: `WorkoutResult` сегодня несёт только `(count, duration)` (`WorkoutViewModel.swift:306`) — дополнить его полями `startDate`/`endDate` (фиксируются в момент `finishWorkout()` / `getWorkoutResult(interrupt: false)`, не в момент тапа «Сохранить») и флагом прерывания (нужен правилу Этапа 5); `WorkoutResult` — Codable, новые опциональные поля безвредны для WC-сериализации на iPhone;
  - опционально: активные калории, пульс — в v1 можно не передавать (для калорий/пульса позже потребуется `HKWorkoutSession` на часах, см. «Технические детали»).
- [ ] Ввести **протокол сервиса** записи тренировки в HealthKit — `HealthKitWorkoutWriting` с двумя методами: «запросить разрешение на запись» и «сохранить тренировку с датами» (оба нужны точкам вызова из Этапа 5, DI — через протокол по правилам проекта; мок в Этапе 2 покрывает оба метода).
- [ ] Там же — **внедрение зависимости** в точку вызова: `WorkoutPreviewViewModel` получает `HealthKitWorkoutWriting` (свойство/параметр инициализатора, без вызова — вызов появится в Этапе 5). До Этапа 4 конкретной реализации нет: в проде по умолчанию `nil` (опционально), в тестах Этапа 2 инжектируется мок — иначе красный тест не скомпилируется.
- [ ] Граница тестируемости: протокол `HealthKitWorkoutWriting` — это **наш сервис** (именно его мокаем в тестах, Этапы 2 и 5); обёртка-протокол над системным `HKHealthStore` не вводится — `HKHealthStore` используется напрямую внутри реализации, тестируемость обеспечивается моком нашего протокола, а корректность записи валидируется на устройстве (критерий Этапа 4, Риски: «Симулятор»).
- [ ] Описать **источник данных** для вызова: только на часах — `WorkoutResult` + время начала (`workoutStartTime` в `WorkoutViewModel`; правило «только с часов» — см. Цель).
- [ ] **Офлайн-first:** обработка недоступности HealthKit и отказа в разрешении — в Этапе 4 (не блокирует сохранение в SwiftData, логируется).

**Критерий завершения:** протокол `HealthKitWorkoutWriting` зафиксирован **в коде** (Watch-таргет, рядом с будущим сервисом из Этапа 4 — мок в Этапе 2 компилируется по нему), описание формата данных — в коде или в документации; согласовано с правилами проекта (без force unwrap, OSLog).

**Критерий завершения:** Watch-таргет собирается с включённым HealthKit; при первом обращении к HealthKit на часах система показывает диалог с указанными описаниями.

## Этап 4: Реализация записи тренировок в HealthKit (Data Layer)

- [ ] Реализовать **сервис записи** (класс/структура, реализующая протокол из этапа 1):
  - запрос разрешения на **запись** типа `HKObjectType.workoutType()` — метод протокола из Этапа 1, асинхронный, без блокировки UI; вызывается однократно при первом входе на экран превью тренировки на часах (Watch-таргет: `WorkoutPreviewViewModel`; точка — Этап 5), не при запуске приложения (см. «Технические детали» → Разрешения);
  - метод: по `startDate` и `endDate` создать `HKWorkout` с типом `HKWorkoutActivityType.crossTraining` и сохранить через `HKHealthStore.save(_:withCompletion:)`.
- [ ] Размещение кода: сервис записи — **только в таргете SotkaWatch Watch App** (см. Цель), например `SotkaWatch Watch App/Services/`.
- [ ] Обработка ошибок: отказ в разрешении, недоступность HealthKit (например, на симуляторе), ошибки `save` — логировать через OSLog (на русском), не прерывать сохранение в SwiftData.
- [ ] Не блокировать UI: вызовы HealthKit асинхронные (async/await или completion handlers); запрос разрешения инициировать из главного потока (показывает системный диалог), `save` UI не блокирует.

**Критерий завершения:** по вызову метода сервиса с датами в «Здоровье» появляется тренировка типа «Кросс-тренинг»; отказ в разрешении не приводит к падению приложения.

## Этап 5: Точка вызова записи в HealthKit (только часы)

- [ ] **Запрос разрешения (часы):** при входе на экран превью тренировки на часах (Watch-таргет: `WorkoutPreviewViewModel`) однократно вызвать запрос разрешения (метод из Этапа 4) — асинхронно, не блокируя переход; отказ не ломает флоу (ошибки записи логируются, см. Этап 4). Диалог может показаться при первом входе в превью ещё до первой завершённой тренировки — это ожидаемо (запрос идемпотентен), отказ не влияет на сохранение в SwiftData.
- [ ] **Apple Watch:** в `WorkoutPreviewViewModel.saveTrainingAsPassed` (кнопка «Сохранить» на экране превью) после успешной отправки `sendWorkoutResult` через `WatchConnectivityService` вызвать сервис записи в HealthKit с датами по правилу из Этапа 1 (критичный путь — сохранение и синхронизация, HealthKit — best-effort; при ошибке отправки в HealthKit не пишем, чтобы «Здоровье» не расходилось с дневником — запишется при повторном сохранении; в отличие от v2 — «Сессия на часах», где запись не зависит от WatchConnectivity, эта привязка в v1 сознательная). Синхронизация с «Здоровье» на iPhone — автоматическая (см. «Требования Apple»).
- [ ] **Прерванные тренировки (стоп) не пишем:** в HealthKit попадает только реально завершённая тренировка (`getWorkoutResult(interrupt: false)`); путь «Стоп» (`WorkoutView` → `cancelWorkout()` → `handleWorkoutResult`) помечается в `WorkoutPreviewViewModel` — при сохранении прерванной через превью запись в HealthKit не вызывается (в SwiftData/дневник — как сейчас).
- [ ] **iPhone:** запись в HealthKit **не вызываем** — ни в `StatusManager.handleSaveWorkoutCommand`, ни при сохранении тренировки с телефона (`WorkoutPreviewViewModel.handleWorkoutResult`) — см. Цель.

**Критерий завершения:** тренировка, выполненная и завершённая на часах, отображается в «Здоровье» на iPhone; тесты из Этапа 2 проходят (TDD — зелёный).

## Риски и ограничения

- **Симулятор:** HealthKit может быть недоступен; тестировать запись на устройстве.
- **Дубликаты:** не актуальны в v1 (один источник — часы). Запись с iPhone — отдельный будущий план; в нём правило: каждая тренировка пишется ровно один раз — с устройства, где выполнена (iPhone не переписывает watch-тренировки, пришедшие по WatchConnectivity), иначе в «Здоровье» будут дубли.
- **Калории и пульс:** не в этом плане — будущий шаг с `HKWorkoutSession` на часах (см. Этап 1 и «Технические детали»); ключ чтения — `NSHealthShareUsageDescription` (см. Этап 3).
- **Одна сессия одновременно** (только при расширении до `HKWorkoutSession`; в v1 сессии нет): если пользователь параллельно начал тренировку в другом приложении, наша сессия получит `errorAnotherWorkoutSessionStarted` — логировать через OSLog, сценарий завершения тренировки не ломать (см. «Требования Apple»).
